ISSUE 7 — Handle GitHub secondary rate limits + jittered backoff in github_fetcher.py (pre-planned #15)
Labels: complexity: medium, help wanted, Wave 9
--------------------------------------------------------------------------------

## Summary
Teach `GitHubClient.get_json` to handle GitHub *secondary* rate limits and add jittered backoff — today only the primary limit (403 + `X-RateLimit-Remaining: 0`) and plain 429 are handled, while GitHub's secondary limits arrive as 403s with a `Retry-After` header and currently crash the fetch.

## Context
`app/scrapers/github_fetcher.py::get_json` raises `GitHubRateLimited` on 403-with-zero-remaining and sleeps on 429, but a 403 carrying `Retry-After` (GitHub's secondary/abuse limit — exactly what a 700-repo, 3-5-calls-per-repo refresh cycle trips) falls through to `resp.raise_for_status()` and raises a raw `HTTPStatusError`. In `app/scheduler/tasks.py::refresh_repos` that exception is caught as a generic failure (`stats["errors"] += 1`) and the repo is skipped instead of the fetch being retried after the indicated wait. Backoff sleeps are also deterministic (`min(2**attempt, 30)`), which synchronizes retries across the many repos in a cycle.

## Acceptance Criteria
- [ ] A 403 response with a `Retry-After` header is treated as a retryable secondary limit: sleep `Retry-After` seconds (capped, e.g. <= 60) and retry within the existing attempt loop
- [ ] Exponential backoff on 5xx/network errors includes random jitter (e.g. `sleep = min(2**attempt, 30) * uniform(0.5, 1.5)`)
- [ ] A 403 secondary limit that persists past `max_retries` raises `GitHubRateLimited` (not `HTTPStatusError`) so `refresh_repos`'s existing `except GitHubRateLimited` abort-and-break path works
- [ ] All existing tests still pass
- [ ] No ruff lint errors

## Technical Notes
All changes are inside `get_json` in `app/scrapers/github_fetcher.py` (the block after `resp = client.get(...)`). Order of checks matters: keep the primary-limit check (`X-RateLimit-Remaining == "0"`) *before* the new `Retry-After` check, since primary 403s can also carry `Retry-After: 0`. Import `random` and use `random.uniform` for jitter. For tests, coordinate with Issue 3 in this batch (the `get_json` unit-test module): if it has landed, extend it; if you land first, create the scaffolding it will extend. Patch `time.sleep` with a recorder and assert: 403+Retry-After sleeps the header value then succeeds on attempt 2, and jitter stays within `[0.5x, 1.5x]` of the base.
